# Документація проєкту

Опис бізнес-завдань і технічних рішень Conference Booking API.
Практичні інструкції із запуску — у [README](../README.md); тут пояснюється, **чому**
систему побудовано саме так.

---

## 1. Бізнес-завдання

Компанія здає конференц-зали в оренду. Сервіс має закрити чотири задачі:

1. **Облік залів.** Адміністратор веде перелік залів, їхню місткість, базову ціну
   та доступні послуги.
2. **Пошук.** Клієнт знаходить зали, вільні у потрібний час і достатні за розміром.
3. **Бронювання.** Клієнт займає зал і одразу бачить прозору вартість.
4. **Аналітика.** Керівництво розуміє, скільки заробляє бізнес і що варто змінити
   в цінах та наборі залів.

### Ключові бізнес-правила

| Правило | Наслідок у коді |
|---|---|
| Зал не можна здати двом клієнтам одночасно | Перевірка перетинів у транзакції `Serializable` |
| Зал звільняється рівно в час завершення | Напіввідкриті інтервали `[start, end)`: 10:00–12:00 і 12:00–14:00 не конфліктують |
| Вартість залежить від часу доби | Тарифні смуги з коефіцієнтами й пріоритетами |
| Пікова націнка перекриває стандартний тариф | Пріоритет смуги, а не порядок у списку |
| Погоджена ціна не змінюється заднім числом | Вартість фіксується знімком у бронюванні |
| Заклад працює 06:00–23:00 | Бронювання поза межами відхиляється |
| Не можна забронювати минуле | Перевірка проти годинника закладу |
| Історія оренди не зникає разом із залом | М'яке видалення + заборона видаляти зал з активними бронями |

## 2. Архітектура

### Чому шари

```
Api  →  Infrastructure  →  Application  →  Domain
```

Залежності спрямовані до центру. Доменний шар не знає ні про EF Core, ні про HTTP,
ні про JSON. Практична вигода:

- **Тестованість.** Розрахунок вартості — чиста функція без БД: 12 тестів виконуються
  за мілісекунди й не потребують інфраструктури.
- **Змінюваність.** Перехід із SQLite на PostgreSQL зачіпає один файл реєстрації
  залежностей. Заміна API-ключів на OAuth2 не торкається контролерів: вони спираються
  на політики авторизації, а не на схему.
- **Читаність.** Бізнес-правило шукається в домені, а не у восьмисотрядковому контролері.

ТЗ окремо наголошує на масштабованості — саме тому межі шарів проведені зараз, поки
проєкт малий. Провести їх пізніше, коли логіка вже розтечеться по контролерах,
коштує на порядок дорожче.

### Агрегати

**`ConferenceRoom`** — корінь агрегату, що володіє переліком своїх послуг (`RoomAmenity`).
Змінити ціну послуги в залі можна лише через зал: так неможливо створити стан,
у якому одна послуга додана до залу двічі.

**`Booking`** — окремий корінь агрегату. Він посилається на зал за ідентифікатором,
але не входить до його агрегату: бронювань з часом стають десятки тисяч, і завантажувати
їх усі разом із залом було б неприйнятно.

**`Amenity`** — каталог послуг закладу. Ціна ж зберігається в `RoomAmenity`, бо ТЗ
передає ціну послуги у складі запиту на створення залу: та сама послуга може коштувати
по-різному в різних залах.

### Об'єкт-значення `BookingPeriod`

Період бронювання — не три окремі поля, а об'єкт із власними інваріантами: кінець
пізніший за початок, тривалість від 30 хвилин до 12 годин, без переходу через опівніч.
Логіка перетину живе тут же, поруч із даними, які вона перевіряє.

### Знімки замість посилань

`Booking` зберігає **назву залу** та **назви й ціни послуг** на момент бронювання.
Це свідома денормалізація: без неї підвищення ціни на проєктор змінило б суми у вже
виставлених рахунках, а перейменування залу зробило б торішні звіти нечитабельними.

## 3. Розрахунок вартості

### Задача

ТЗ задає чотири тарифні смуги, з яких **пікові години (12:00–14:00) лежать усередині
стандартних (09:00–18:00)**. Бронювання може перетинати кілька смуг.

### Рішення

Модель «тарифна смуга з пріоритетом»:

```csharp
record PricingBand(string Name, TimeOnly Start, TimeOnly End, decimal Multiplier, int Priority);
```

Алгоритм:

1. Зібрати точки розрізу: межі бронювання + усі межі смуг усередині нього.
2. Для кожної ділянки знайти смугу з **найвищим пріоритетом**, що її покриває.
3. `сума ділянки = базова ставка × коефіцієнт × години`.
4. Додати разові платежі за послуги.

Пікова смуга має пріоритет 100 проти 10 у стандартної, тож 12:00–14:00 завжди
рахується з націнкою.

### Чому не простий `switch` за годиною

Перебір годин у `switch` виглядав би коротшим, але:

- ламався б на півгодинних слотах (12:00–12:30);
- вимагав би зміни коду щоразу, коли бізнес зсуває межу смуги;
- не давав би деталізації, яку клієнт бачить у відповіді.

Тарифна сітка натомість приходить із `appsettings.json` і перевіряється на старті:
суперечлива конфігурація не дасть застосунку піднятися, замість того щоб тихо
порахувати чиюсь оренду безкоштовно.

### Гроші

- Тип `decimal`, ніколи `double`: накопичена похибка в підсумках рахунків неминуче
  проявиться в звітності.
- Округлення `MidpointRounding.AwayFromZero` — так рахує бухгалтерія, і саме такий
  результат очікує клієнт (банківське округлення .NET за замовчуванням дало б інший).
- У БД — `decimal(18,2)`.

## 4. Захист від подвійного бронювання

Наївна реалізація виглядає так:

```csharp
if (!await HasOverlapAsync(...)) { Add(booking); await SaveAsync(); }
```

Між перевіркою і вставкою є вікно, у яке проходить паралельний запит — і зал
продається двічі. Тому обидві операції виконуються в одній транзакції з рівнем
ізоляції `Serializable`:

```csharp
await _unitOfWork.ExecuteInTransactionAsync(async ct =>
{
    if (await _bookings.HasOverlapAsync(room.Id, period, ct))
        throw new ConflictException("time_slot_taken", ...);

    _bookings.Add(created);
    await _unitOfWork.SaveChangesAsync(ct);
    return created;
}, cancellationToken);
```

Транзакція виконується через `IExecutionStrategy` — інакше повтор при транзієнтній
помилці впав би з `InvalidOperationException` на провайдерах із політикою повторів.

> **Наступний крок при переході на PostgreSQL:** додати `EXCLUDE USING gist`
> на `(room_id, tsrange(start_at, end_at))` для підтверджених бронювань. Це перенесе
> гарантію в СУБД і зробить її незалежною від рівня ізоляції.

## 5. Обробка помилок

Один `ExceptionHandlingMiddleware` перетворює винятки на відповіді
[RFC 7807](https://www.rfc-editor.org/rfc/rfc7807):

| Виняток | HTTP | Приклад |
|---|---|---|
| `ValidationException` | 400 | Некоректний email |
| `EntityNotFoundException` | 404 | Немає такого залу |
| `ConflictException` | 409 | Час зайнято |
| `DomainException` | 422 | Перевищено місткість |
| решта | 500 | Непередбачений збій |

Кожна відповідь містить машиночитний `code` (щоб клієнт реагував програмно,
не парсячи текст) і `traceId` (щоб звернення в підтримку можна було зіставити з логом).

Розділення 409 і 422 навмисне: 409 означає «спробуйте інший час», 422 — «змініть
параметри запиту». Клієнтський застосунок має реагувати на них по-різному.

Деталі внутрішніх помилок клієнту не потрапляють — повідомлення винятку може містити
рядок підключення, шлях на диску чи фрагмент SQL. Повний стектрейс лишається в логах.

## 6. Безпека

### Автентифікація

API-ключі в заголовку `X-Api-Key`. Обрано свідомо: клієнти цього API — системи
партнерів, а не люди в браузері, тож повний OAuth2-цикл був би надлишковим.
Контролери спираються на **політики авторизації**, а не на схему автентифікації,
тому додавання OIDC поверх не зачепить жодного контролера.

Ключі порівнюються **за сталий час** через SHA-256 і `CryptographicOperations.FixedTimeEquals`.
Звичайне порівняння рядків завершується на першому відмінному символі, і за різницею
часу відповіді ключ відновлюється символ за символом.

### Fallback-політика

```csharp
.SetFallbackPolicy(new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build())
```

Маршрут без явного `[Authorize]` усе одно вимагає автентифікації. Забути атрибут
на новому контролері не має означати відкритий доступ — безпека за замовчуванням,
а не за уважністю розробника.

### Решта

- **Rate limiting** — 120 запитів/хв на ключ або IP: захист від перебору ключів
  і від того, щоб один клієнт вичерпав ресурси для решти.
- **Валідація на межі** — FluentValidation через фільтр, що застосовується до всіх
  дій автоматично: перевірку неможливо забути додати в новому методі.
- **CORS закритий за замовчуванням.** `AllowAnyOrigin` тихо відкрив би API будь-якому
  сайту, тому дозволені походження задаються явно.
- **Заголовки безпеки** та приховування `Server`/`X-Powered-By`.
- **Параметризовані запити** EF Core — SQL-ін'єкції неможливі за побудовою.

## 7. Робота з даними

### Нормалізовані назви замість колації БД

Спершу унікальність назв спиралася на колацію SQLite `NOCASE`. Тести показали,
що вона згортає регістр **лише для латиниці ASCII**: «Зал А» і «зал а» вважалися
різними назвами.

Рішення — окрема колонка `NormalizedName` (`ToUpperInvariant`), за якою працюють
унікальний індекс і пошук. Поведінка стала однаковою для будь-якої мови і перестала
залежати від провайдера БД.

### Ідентифікатори

Корені агрегатів (`ConferenceRoom`, `Booking`, `Amenity`) генерують `Guid` у власних
конструкторах — ідентифікатор потрібен їм одразу, ще до збереження. Дочірні сутності
(`RoomAmenity`, `BookingAmenity`) лишають його порожнім: EF заповнює його при вставці.

Це не стилістичний вибір. Якщо дочірня сутність приходить із уже заповненим ключем,
EF приймає її за наявний рядок і генерує `UPDATE` замість `INSERT` — операція
не зачіпає жодного рядка й падає з `DbUpdateConcurrencyException`.

### М'яке видалення

Зал позначається як видалений, а не стирається. Причина суто бізнесова: фінансова
звітність за минулі періоди має лишатися коректною. Унікальний індекс на назву
відфільтровано за `IsDeleted = 0`, тож звільнена назва одразу доступна для нового залу.

Видалити зал, у якого є **активні майбутні броні**, не можна взагалі: тихе зникнення
залу означало б зірвані заходи в клієнтів, які вже все оплатили й запросили людей.

### Індекси

| Індекс | Навіщо |
|---|---|
| `Bookings (RoomId, StartAt, EndAt)` | Головний індекс сервісу: перевірка перетинів на кожне бронювання і кожен пошук |
| `Bookings (Date)`, `Bookings (Status)` | Вибірки для звітів |
| `Rooms (NormalizedName)` унікальний, фільтрований | Унікальність назв серед активних залів |
| `RoomAmenities (RoomId, AmenityId)` унікальний | Одна послуга не може бути двічі в одному залі |

Звіти читають дані з `AsNoTracking()`: тримати тисячі бронювань у трекері змін —
марна витрата пам'яті й часу на кожному `SaveChanges`.

## 8. Час і часові пояси

Тарифні смуги з ТЗ задані **настінним часом**: «вечірня знижка з 18:00» має означати
18:00 на годиннику в холі, незалежно від того, де стоїть сервер і чи був перехід
на літній час.

Тому бронювання зберігаються в локальному часі закладу, а часовий пояс задається
явно в конфігурації (`Venue:TimeZoneId`), а не береться з налаштувань сервера.
Поля аудиту (`CreatedAtUtc`, `CancelledAtUtc`) — навпаки, в UTC: вони фіксують
момент події, а не робочий розклад.

Поточний час подається через `IDateTimeProvider`, тож правило «не можна бронювати
заднім числом» перевіряється тестами й не залежить від дати запуску збірки.

## 9. Звіти

Звіти будувалися від управлінських рішень, а не від наявних таблиць.

| Звіт | Рішення, яке він підтримує |
|---|---|
| `summary` | Загальний стан справ за період |
| `room-utilization` | Який зал недозавантажений (знижка, перепрофілювання), який витримає підвищення ціни. Середня заповненість показує, чи не продають великий зал під маленькі зустрічі |
| `revenue` | Планування й сезонність |
| `amenity-demand` | Які послуги докупити в інші зали, а які не окуповують обслуговування |
| `hourly-load` | Чи збігаються «пікові години» з тарифів із реальним піком попиту |
| `pricing-bands` | Скільки коштували знижки і скільки принесла націнка — у гривнях |

### Атрибуція виторгу за смугами без додаткових таблиць

`pricing-bands` має показати виторг у розрізі тарифних смуг, але бронювання зберігає
лише підсумкові суми. Зберігати ще й деталізацію означало б дублювати дані,
які можна вивести.

Оскільки `RoomCost = базова ставка × Σ(години_i × коефіцієнт_i)`, базову ставку
можна відновити точно:

```csharp
var reference = calculator.Calculate(1m, booking.Period, []);
var effectiveBaseRate = booking.RoomCost / reference.RoomCost;
```

Далі та сама сітка застосовується до відновленої ставки. Результат точний, зайвих
даних не зберігається, а звіт лишається коректним навіть після зміни ціни залу —
бо ставка виводиться з **фактично виставленої суми**, а не з поточного прайсу.

Той самий прийом відновлює `cost.segments` для збереженого бронювання.

## 10. Тестування

**65 тестів.** Пріоритет — логіка, помилка в якій коштує грошей або репутації.

- **Розрахунок вартості** покрито найщільніше: кожна смуга окремо, перетини смуг,
  пріоритет піку над стандартом, півгодинні слоти, послуги, час поза робочими годинами,
  збіг суми ділянок із підсумком.
- **Сценарні тести** працюють поверх **реального SQLite у пам'яті**. InMemory-провайдер
  EF Core не має ні транзакцій, ні обмежень цілісності — саме ті помилки, які ці тести
  мають ловити, він би пропустив. Цей вибір уже окупився: на реальному провайдері
  спливла проблема з ідентифікаторами дочірніх сутностей (розділ 7).
- **Числа в тестах взяті з ТЗ**: «Зал А» 2000 грн/год, 10:00–14:00 → 8600 грн оренди.
  Тест читається як перевірка вимоги, а не як перевірка реалізації.

## 11. Що далі

Свідомо не увійшло в обсяг завдання, але передбачено архітектурою:

| Напрям | Готовність |
|---|---|
| PostgreSQL | Заміна провайдера в одному файлі; `EXCLUDE`-обмеження замість покладання на рівень ізоляції |
| OAuth2 / OIDC | Контролери спираються на політики — додається як ще одна схема автентифікації |
| Кабінет клієнта | `Booking` уже зберігає замовника; потрібна прив'язка до облікового запису |
| Сповіщення | Точки виклику — створення та скасування бронювання |
| Пагінація | Потрібна для переліків, коли залів і бронювань стане багато |
| Кешування переліку залів | Дані змінюються рідко, а читаються на кожному пошуку |
| Розширений аудит | Поля `CreatedAtUtc` / `UpdatedAtUtc` уже є; бракує автора зміни |
